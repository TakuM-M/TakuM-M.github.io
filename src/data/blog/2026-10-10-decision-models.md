2026年9月15日から、**Decision Model** と呼ばれる AI モデルが相次いで公開されています。
文章は生成せず、「どれか一つ選ぶ」「Yes か No か」といった決まった形の質問に、確率付きで答えるモデルです。

本記事では、Jev、Jev と API 互換のオープンモデル Laya、比較用の LLM 2 つを同じデータで測った結果を中心に、仕組みと最近の動向をまとめます。

## Decision Model の登場

- **9/15**: TypeSafe AI が Jev を公開
- **9/29**: Liquid AI が d1 を公開
- **9/30**: OpenAI が Decisions API を発表（10/6 に public beta）
- **10/1**: Cloudflare が Clef を、Perplexity が pplx-decider を公開
- **10/7**: Liquid AI が d1-3B と d1-omni-600M の重みを公開

3 週間あまりで Liquid AI、OpenAI、Cloudflare、Perplexity が続き、Decision Model は一気に注目されました。

発端は TypeSafe AI の **Jev** です。TypeSafe はこれを「System One model」と呼んでいます。

Jev には、判定したいデータ（`state`）と型付きの質問（`questions`）を渡します。
質問の型は次の 3 つで、返ってくるのは文章ではなく確率です。

| 型 | 答えの形 | 例 |
|---|---|---|
| `choice` | 選択肢の中から 1 つ（全選択肢の確率付き） | このログは payment / auth / … のどれか |
| `noul` | Yes の確率 | このメールはスパムか |
| `score` | 順序尺度上の位置 | この問い合わせの緊急度は 1〜4 でどのくらいか |

文章を生成しないので、LLM と比べて料金が安く、レスポンスも速いのが特徴です。

注目された理由は、LLM に任せている仕事の多くが、実は文章を必要としていないからだと考えられます。
問い合わせの振り分け、ログの分類、エージェントのツール選択、出力のガードレールなどで欲しいのは、ラベル 1 つとその確率だけです。
これを LLM でやると、毎回プロンプトを読ませて答えを書かせることになり、遅く、コストもかかります。

## LLM と Decision Model の違い

![LLM と Decision Model の推論の違いを示した図。LLM はトークンを 1 つずつ生成し、Decision Model は 1 回の推論で全選択肢の確率を返す](/images/2026-10-10-decision-models/mechanism.svg "fig1:LLM（上）と Decision Model（下）の推論の違い")

### LLM はトークンを生成する

LLM で映画レビューの感情を分類すると、`{"label":"positive"}` のような答えを 1 トークンずつ生成します（fig1 上）。
トークンを 1 つ出すたびにモデル全体を通すので、出力が長いほど推論の回数が増えます。
JSON スキーマで出力をラベル名に縛っても、「書いて答える」ことは変わりません。

確率もトークン単位でしか得られません。`positive` が `pos` と `itive` に分かれるように、ラベルが複数のトークンにまたがると、ラベル全体の確率は直接取り出せません。

プロンプトで「確率も 0〜1 で答えて」と頼めば、`{"label":"positive","confidence":0.9}` のように確率らしき値を出させることはできます。
ただし、この値はモデルが内部で計算した確率ではなく、確率っぽく書いたテキストです。
高めの値に偏りやすく、聞き方や乱数で値が変わり、実際の正解率と一致する保証もありません。

### Decision Model は 1 回で全選択肢の確率を返す

Decision Model は生成をしません（fig1 下）。
入力を本体に 1 回だけ通し、全選択肢の確率をまとめて返します。

Jev は中身を公開していないので、ここでは重みとコードが公開されている Laya で仕組みを見ます。
API の形は Jev と同じです。

Laya は、質問・選択肢・判定したいテキストを 1 本の入力につなげ、各選択肢の頭に目印の `[MASK]` を置きます。

```
[CLS] 質問 [SEP] [MASK] positive [MASK] neutral [MASK] negative [SEP] 最高の映画だった！ [SEP]
```

これを本体に 1 回通したあと、**判定ヘッド** が各 `[MASK]` の位置の内部表現から選択肢ごとのスコア $s_c$ を出し、softmax で確率にします。

$$
  p(c \mid x, q) = \frac{\exp(s_c)}{\sum_{c' \in C_q} \exp(s_{c'})}
$$

$x$ は判定したいテキスト、$q$ は質問、$C_q$ はその質問の選択肢の集合です。
$C_q$ についてだけ和をとるので、**選択肢の外の答えは構造上出ません**。
また、全選択肢の確率が返るので、「positive が 0.92、neutral が 0.06」のように迷い具合まで分かります。

ほかの型も同じ仕組みの上に乗っています。
`noul` は Yes / No を true / false の 2 択として扱い、true の確率を返します。
`score` は各段階を選択肢として確率を出し、その期待値を返します。
たとえば 0〜2 の 3 段階で確率が 0.00 / 0.57 / 0.43 なら、答えは $0 \times 0.00 + 1 \times 0.57 + 2 \times 0.43 = 1.43$ です。

本体の構成はモデルごとに異なります。

| モデル | 本体 | 備考 |
|---|---|---|
| Laya | ModernBERT-large（エンコーダ） | 重み公開。ヘッド込みで 421M パラメータ。Laya の設定で入力上限 512 tokens（ModernBERT 自体は 8,192 tokens まで扱える） |
| Jev | 非公開 | 論文も未公開。エンコーダ説、LLM + ヘッド説などがある |

小さなエンコーダを使う Laya はノート PC でも動きますが、入力枠が小さいという弱点があります。

## ベンチマークの実施

コードは [hellow-jev](https://github.com/TakuM-M/hellow-jev) に置いています。

### 条件

比較したのは次の 4 つです。Laya はファインチューニングもできますが、今回はすべてゼロショットで評価しました。

| | API | ローカル（Apple M1, 8GB） |
|---|---|---|
| Decision Model | Jev 1.13（TypeSafe） | Laya（english、laya-serve 経由） |
| LLM | Claude Haiku 4.5 | Qwen3 4B Instruct（Ollama） |

ローカルの PC は Apple M1（8 コア）、メモリ 8GB、macOS 26.6.2 です。Qwen3 4B は `qwen3:4b-instruct` を使いました。

データは、先行ベンチマークの [jevbench](https://github.com/dhruvmehra/jevbench) と同じサンプル（各 500 件、seed=0）を使いました。

- **SST-2**: 映画レビューの感情（2 クラス）
- **AG News**: ニュースの話題（4 クラス）。v2 はラベルの説明文だけを書き直したもの
- **Banking77**: 銀行アプリの問い合わせ意図（77 クラス）

ラベル名と説明文は全モデルで同じです。LLM は JSON スキーマでラベル名の enum に縛り、temperature は 0 にしました。
レイテンシは 1 件ずつ逐次に投げたときのクライアント側の往復時間で、API はネットワーク込みです。

### 精度

![4 タスクそれぞれについて、4 モデルの正解率を並べた棒グラフ](/images/2026-10-10-decision-models/accuracy.svg "fig2:タスク別の正解率（各 n=500、2026-09-29 計測）")

| model | SST-2 | AG News | AG News v2 | Banking77 |
|---|---:|---:|---:|---:|
| Jev | 0.950 | 0.844 | 0.856 | **0.768** |
| Laya | 0.920 | **0.906** | **0.862** | 0.382 |
| Claude Haiku 4.5 | **0.960** | 0.832 | 0.850 | 0.758 |
| Qwen3 4B | 0.940 | 0.784 | 0.766 | 0.662 |

- **Jev は Haiku 4.5 とほぼ同じ精度**です。77 クラスの Banking77 でも 0.768 と 0.758 で並びました。n=500 なので、1〜2pt の差は誤差の範囲です
- **Laya はクラスが少ないと強いのに、77 クラスで崩れます**（0.382）。前の節で書いた入力枠の問題で、全選択肢の説明が 512 tokens の枠を分け合うため、77 個も並べると説明が入りきりません。Laya のドキュメントでも選択肢は 20 個程度までが推奨されています

AG News の説明文を書き直した v2 では、Jev +1.2pt、Haiku +1.8pt と少し上がった一方、Laya は −4.4pt、Qwen は −1.8pt と下がりました。上がった幅は誤差の範囲ですが、同じ指示でもモデルによって反応が違うので、Decision Model でも「説明文のチューニング」は必要そうです。

### 速さ

![4 タスクそれぞれについて、4 モデルの 1 件あたりレイテンシ p50 を並べた棒グラフ](/images/2026-10-10-decision-models/latency.svg "fig3:タスク別のレイテンシ p50（Jev・Haiku はネットワーク込み、Laya・Qwen は M1 上）")

| model | SST-2 | AG News | AG News v2 | Banking77 |
|---|---:|---:|---:|---:|
| Jev | 168 ms | 169 ms | 165 ms | 175 ms |
| Laya | 102 ms | 141 ms | 178 ms | 279 ms |
| Claude Haiku 4.5 | 799 ms | 749 ms | 768 ms | 820 ms |
| Qwen3 4B | 686 ms | 990 ms | 954 ms | 1,416 ms |

Jev はネットワーク込みで 170 ms 前後、**Haiku の約 1/5** でした。選択肢が 2 個でも 77 個でもほとんど変わらないのが特徴的です。
Laya は 8GB の M1 でもこの速さで動くのが魅力ですが、選択肢や説明文が増えて入力が長くなるほど遅くなります。
同じ M1 で比べると、Qwen3 4B は Laya の 5〜7 倍かかりました。モデルが約 10 倍大きいことに加え、答えを生成する分の差だと考えられます。

なお Jev の公称値は「LLM の 100 倍速い」ですが、比べる相手次第です。今回の Haiku 4.5 相手だと約 5 倍でした。

### コスト

Banking77 の 500 件を流したときの料金は、Jev が約 \$0.04、Haiku 4.5 が約 \$1.14 でした。
1 万件あたりに直すと Jev が **\$0.83**、Haiku 4.5 が **\$22.88** で、約 28 倍の差です。

料金は、API が返したトークン数に計測時点の公式単価（Jev は入力 \$0.042 / MTok で出力は無料、Haiku は入力 \$1・出力 \$5 / MTok）を掛けて出しています。
入力トークン数はほぼ同じなので、差のほとんどは入力単価の違いから来ています。

### 確率の活用

Decision Model の一番の利点は、精度よりも **確率が返ってくること** だと思います。
確率が低い判定だけを人に回す運用を想定して、Jev で **1 位の選択肢の確率**が 0.9 未満なら「保留」にした場合の試算が次の表です。

| タスク | 全件の Acc | 保留率 | 保留後の Acc |
|---|---:|---:|---:|
| SST-2 | 0.950 | 11.8% | 0.982 |
| AG News | 0.844 | 13.6% | 0.903 |
| Banking77 | 0.768 | 30.6% | 0.899 |

Jev は SST-2 と AG News なら 1 割強を人に回すだけで、保留後の正解率が 3〜6pt 上がります。Banking77 でも 3 割を回せば、保留後は 0.90 近くまで上がります。確率が「間違いやすさ」の手がかりとしてちゃんと機能しているということです。

ただし、Jev の確率も手放しで信じられるわけではありません。
AG News で Jev が間違えた問題を見ると、そのときの確率の中央値は 0.93 でした。つまり、間違えた問題の半分以上で 0.9 以上の確率を出していて、閾値 0.9 では保留にできません。
閾値はタスクごとに検証データで決める必要があり、それでも高い確率のまま間違えるケースは残る、という前提で運用することになりそうです。

## その他のモデル

ベンチマークを回している間にも、新しい Decision Model が次々と出てきました。比較のため、Jev の入力単価は \$0.042 / MTok です。

| モデル | 提供元 | 公開日 | 重み | 入力単価（/ MTok） |
|---|---|---|---|---|
| d1 | Liquid AI | 9/29 | 一部公開 | \$0.04 |
| Decisions API | OpenAI | 9/30 | 非公開 | 非公開 |
| Clef | Cloudflare | 10/1 | 公開 | \$0.24 |
| pplx-decider | Perplexity | 10/1 | 公開 | \$0.02（10/6 の v1.1 以降） |

- **d1（Liquid AI）**: 10/7 に小型版の d1-3B と d1-omni-600M の重みを公開しました。d1-omni-600M は画像や音声も入力でき、端末上での判定を狙っています
- **Decisions API（OpenAI）**: 9/30 に発表され、10/6 に public beta になりました。中身のモデルは gpt-6-luna です。考え方は Jev と同じですが、`state` が `input` に、選択肢を配列で渡すなど、リクエストの形が少し違います。Yes / No の型は `predicate` という名前です
- **Clef（Cloudflare）**: Qwen 系の LLM（27B / 9B）を入力の読み込み（prefill）だけに使い、判定ヘッドを付けたタイプです。27B の Clef と 9B の Clef-flash（入力 \$0.09）があり、Workers AI の API で使えます。重みは Apache-2.0 で公開されていますが、専用の判定ヘッドが要るので vLLM などではそのまま動きません
- **pplx-decider（Perplexity）**: 27B の重み公開モデルです。10/6 の v1.1 で入力単価を \$0.02 まで下げました

## 今後の動向の予測

最後に、この 1 か月の動きを見て考えた、今後の予想を書いておきます。

1. **API の形がそろっていく**  
    d1、Clef、Laya は Jev と同じ形の API を採用していて、OpenAI だけが少し違う形です。LLM API は先行した OpenAI の形に収束しましたが、今回は先行した Jev の形に多数派がそろっている点が違います。Decision Model では `state` + `questions` という形が事実上の標準になっていくと思います。そうなれば、モデルの乗り換えは設定 1 行で済むようになり、価格と精度だけで選ばれる世界になります。

2. **単価は 0 に近づき、差がつくのは確率の質になる**  
    1 か月で入力単価は \$0.042 → \$0.02 まで下がりました。単価で差がつかなくなると、正解率に加えて、確率の質（返す確率が実際の正解率と合っているか）が重要な指標になるとみています。

3. **LLM と Decision Model の分業が当たり前になる**  
    エージェントが毎ステップ大きな LLM で考えるのではなく、ツールの選択やガードレールのような各ステップの細かい判断は Decision Model に任せ、確率が低いときだけ LLM や人に回す構成が増えていくと思います。

4. **ローカル・端末上への広がり**  
    Laya や d1-omni-600M のように、小さなモデルを手元で動かす流れも続くはずです。ただし今回の Laya の Banking77 のように、小さいモデルには選択肢の数や入力の長さという明確な限界があります。用途に合わせて API と使い分けることになりそうです。

5. **LLM の前段に Decision Model の層が重なる**  
    これは言語モデルのアルゴリズム自体に対しての予想です。これからの LLM システムは、入口に何層もの Decision Model を持つ構成になるのではないかと考えています（fig4）。まず Decision Model が「何の仕事か」「何が必要か」「どれくらい難しいか」と分類を重ねて依頼を絞り込み、その結果に合ったハーネス（ツールやプロンプトなどの実行環境）を持つ LLM が最後に動き出す、という形です。

    ![上に Decision Model の層が 4 段重なり、入力が各層で 1 つずつ選ばれながら下へ進み、最下段の LLM ＋ ハーネスにたどり着く台形の図](/images/2026-10-10-decision-models/future.svg "fig4:Decision Model の層で絞り込んでから LLM が生成する構成（筆者の予想）")

    分類の層はどれも 1 回の推論で済むので、速く安く動きます。確率が返るので、どの層で迷ったかも分かります。今は 1 つの LLM が判断も生成もまとめて担っていますが、その前段は、細かい判断を積み重ねる Decision Model に置き換わっていくのではないでしょうか。
