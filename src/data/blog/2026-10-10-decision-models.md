先月半ばから、**Decision Model（判定モデル）** と呼ばれる AI モデルが相次いで公開されています。
文章は生成せず、「どれか一つ選ぶ」「Yes か No か」といった決まった形の質問に、確率付きで答えるモデルです。

本記事では、火付け役の Jev、オープンな互換モデル Laya、比較用の LLM 2 つを同じデータで測った結果を中心に、仕組みと最近の動向をまとめます。

## 先月から始まったトレンド

- **9/15**: TypeSafe AI が Jev を公開
- **9/29**: Liquid AI が d1 を公開
- **9/30**: OpenAI が Decisions API を発表（10/6 に public beta）
- **10/1**: Cloudflare が Clef を、Perplexity が pplx-decider を公開
- **10/7**: Liquid AI が d1-3B と d1-omni-600M の重みを公開

発端は TypeSafe AI の **Jev** です。TypeSafe はこれを「System One model」と呼んでいます。
カーネマンの言う、速く直感的な「システム 1」に由来する名前で、じっくり考えて文章を書く LLM（システム 2）との役割分担を意識しています。

Jev には、判定したいデータ（`state`）と型付きの質問（`questions`）を渡します。
質問の型は次の 3 つで、返ってくるのは文章ではなく確率です。

| 型 | 答えの形 | 例 |
|---|---|---|
| `choice` | 選択肢の中から 1 つ（全選択肢の確率付き） | このログは payment / auth / … のどれか |
| `noul` | Yes の確率 | このメールはスパムか |
| `score` | 順序尺度上の位置 | この問い合わせの緊急度は 1〜4 のどれか |

文章を生成しないので出力は無料で、料金は入力 \$0.042 / 1M tokens だけです。
Vercel の AI Gateway では、掲載から 24 時間で有料チームの約 13% が使い始めたそうです。

その後 3 週間で Liquid AI、OpenAI、Cloudflare、Perplexity が続き、判定モデルは 1 製品から一つのジャンルになりました。

注目された理由は、LLM に任せている仕事の多くが、実は文章を必要としていないからだと思います。
問い合わせの振り分け、ログの分類、エージェントのツール選択、出力のガードレールなどで欲しいのは、ラベル 1 つとその確信度だけです。
これを LLM でやると、毎回プロンプトを読ませて答えを書かせることになり、遅くコストもかかります。

## どんな原理で動いているのか

![LLM と判定モデルの推論の違いを示した図。LLM はトークンを 1 つずつ生成し、判定モデルは 1 回の推論で全選択肢の確率を返す](/images/2026-10-10-decision-models/mechanism.svg "fig1:LLM（上）と判定モデル（下）の推論の違い")

### LLM は答えを 1 トークンずつ書く

LLM でログを分類する場合、たとえば `{"label":"performance"}` という答えを、`{"`、`label`、`":"`、`perf`… と 1 トークンずつ生成します（fig1 上）。
1 トークン出すたびにモデル全体を 1 回通すので、出力が長いほど推論の回数が増えます。
JSON スキーマでラベル名以外を出せないように縛ることはできますが、それでも「書いて答える」ことに変わりはありません。

また、LLM が出す確率はトークン単位です。`performance` が `perf` + `ormance` に分かれるように、ラベルが複数トークンに分かれると、「performance である確率」をそのまま取り出すのは簡単ではありません。

### 判定モデルは 1 回通して、全選択肢の確率を返す

判定モデルは生成をしません（fig1 下）。
判定したいテキストと、質問・選択肢の説明をまとめてモデル本体に 1 回だけ通し、得られた内部表現を **判定ヘッド** に渡します。
判定ヘッドは選択肢ごとにスコア $s_c$ を出し、softmax で確率にします。

$$
  p(c \mid x, q) = \frac{\exp(s_c)}{\sum_{c' \in C_q} \exp(s_{c'})}
$$

ここで $x$ は判定したいテキスト、$q$ は質問、$C_q$ はその質問の選択肢の集合です。
分母が選択肢の集合 $C_q$ の上でしか和をとっていないので、**選択肢の外の答えは構造上出ません**。
そして全選択肢の確率がそろって返ってくるので、「performance が 0.78、normal が 0.14」のように、どれくらい迷っているかまで分かります。

`noul`（Yes / No）は sigmoid で Yes の確率を、`score` は段階ごとの確率から期待値を出す、と説明されています。
質問が複数あっても、同じ内部表現から全部の答えを並列に出せます。

本体に何を使うかはモデルによって違います。

| モデル | 本体 | 備考 |
|---|---|---|
| Laya | ModernBERT-large（421M、エンコーダ） | 重み公開。入力上限 512 tokens |
| Clef（Cloudflare） | Qwen 系 27B / 9B の LLM | LLM を prefill（入力の読み込み）だけ回し、判定ヘッドを付ける |
| Jev | 非公開 | 論文も未公開。エンコーダ説、LLM + ヘッド説などがある |

Clef の作りは面白くて、LLM を「読むだけ」に使っています。
LLM の推論は、入力をまとめて読む prefill と、1 トークンずつ書く decode に分かれますが、遅いのは decode の方です。判定モデルは decode を丸ごと捨てているので、大きな LLM を本体にしても速く動きます。

逆に小さいエンコーダを本体にした Laya は、手元のノート PC でも動く代わりに、入力枠が小さいという弱点を抱えています。これは後のベンチマークで効いてきます。

## ベンチマークをやってみた

公称値だけではよく分からないので、自分で測りました。コードは [hellow-jev](https://github.com/TakuM-M/hellow-jev) に置いています。

### 条件

比較したのは次の 4 つです。ファインチューニングはせず、全部ゼロショットです。

| | API | ローカル（Apple M1, 8GB） |
|---|---|---|
| 判定モデル | Jev 1.13（TypeSafe） | Laya（english、laya-serve 経由） |
| LLM | Claude Haiku 4.5 | Qwen3 4B Instruct（Ollama） |

データは、先行ベンチマークの [jevbench](https://github.com/dhruvmehra/jevbench) と同じ抽出（各 500 件、seed=0）を使いました。

- **SST-2**: 映画レビューの感情（2 クラス）
- **AG News**: ニュースの話題（4 クラス）。v2 はラベルの説明文だけを書き直したもの
- **Banking77**: 銀行アプリの問い合わせ意図（77 クラス）

ラベル名と説明文は全モデルで同じです。LLM は JSON スキーマでラベル名の enum に縛り、temperature は 0 にしました。
レイテンシは 1 件ずつ逐次に投げたときのクライアント側の往復時間で、API はネットワーク込みです。

まず jevbench の公表値と突き合わせたところ、Jev は 0.6pt 以内、Laya は小数第 3 位まで一致しました。測り方は jevbench と合っていると考えてよさそうです。

### 精度

![4 タスクそれぞれについて、4 モデルの正解率を並べた棒グラフ](/images/2026-10-10-decision-models/accuracy.svg "fig2:タスク別の正解率（各 n=500、2026-09-29 計測）")

| model | SST-2 | AG News | AG News v2 | Banking77 |
|---|---:|---:|---:|---:|
| Jev | 0.950 | 0.844 | 0.856 | **0.768** |
| Laya | 0.920 | **0.906** | **0.862** | 0.382 |
| Claude Haiku 4.5 | **0.960** | 0.832 | 0.850 | 0.758 |
| Qwen3 4B | 0.940 | 0.784 | 0.766 | 0.662 |

n=500 だと 95% 信頼区間はおよそ ±2〜3pt なので、それより小さい差は「同じくらい」と読むのが妥当です。そう読むと、

- **Jev は Haiku 4.5 とほぼ同じ精度**です。77 クラスの Banking77 でも 0.768 と 0.758 で並びました
- **Laya はクラスが少ないと強いのに、77 クラスで崩れます**（0.382）。前の節で書いた入力枠の問題で、全選択肢の説明が 512 tokens の枠を分け合うため、77 個も並べると説明が入りきりません。Laya 自身も選択肢は 20 個程度までを推奨しています
- Qwen3 4B は全体的に一段低めでした

AG News の説明文を書き直した v2 では、Jev +1.2pt、Haiku +1.8pt と少し上がった一方、Laya は −4.4pt と下がりました。同じ指示でもモデルによって反応が違うので、判定モデルでも「説明文のチューニング」は必要そうです。

### 速さ

![4 タスクそれぞれについて、4 モデルの 1 件あたりレイテンシ p50 を並べた棒グラフ](/images/2026-10-10-decision-models/latency.svg "fig3:タスク別のレイテンシ p50（Jev・Haiku はネットワーク込み、Laya・Qwen は M1 上）")

| model | SST-2 | AG News | AG News v2 | Banking77 |
|---|---:|---:|---:|---:|
| Jev | 168 ms | 169 ms | 165 ms | 175 ms |
| Laya | 102 ms | 141 ms | 178 ms | 279 ms |
| Claude Haiku 4.5 | 799 ms | 749 ms | 768 ms | 820 ms |
| Qwen3 4B | 686 ms | 990 ms | 954 ms | 1,416 ms |

Jev はネットワーク込みで 170 ms 前後、**Haiku の約 1/5** でした。選択肢が 2 個でも 77 個でもほとんど変わらないのが特徴的です。
Laya は 8GB の M1 でもこの速さで動くのが魅力ですが、選択肢が増えるほど遅くなります。
同じ M1 で比べると、Qwen3 4B は Laya の 5〜7 倍かかりました。こちらは生成する分と、プロンプトが長い分の差です。

なお Jev の公称値は「LLM の 100 倍速い」ですが、比べる相手次第です。今回の Haiku 4.5 相手だと約 5 倍でした。

### コスト

Banking77 の 1 万件あたりで比べると、Jev が **\$0.83**、Haiku 4.5 が **\$22.88** で、約 27 倍の差がありました。
Jev は入力単価が安いうえ出力が無料なのに対して、Haiku は JSON スキーマの分だけ入力トークンが膨らむこともあり、差が開きます。
ちなみに jevbench の公表値では、Claude Sonnet 5 は同じ条件で \$64.33 です。

### 確率が使える

判定モデルの一番の利点は、精度よりも **確率が返ってくること** だと感じました。
確率が低い判定だけを人に回す運用を想定して、閾値 0.9 未満を「保留」にした場合の試算が次の表です。

| model | タスク | そのままの Acc | 保留率 | 保留しなかった分の Acc |
|---|---|---:|---:|---:|
| Jev | SST-2 | 0.950 | 11.8% | 0.982 |
| Jev | AG News | 0.844 | 13.6% | 0.903 |
| Jev | Banking77 | 0.768 | 30.6% | 0.899 |
| Laya | AG News | 0.906 | 45.2% | 0.974 |
| Laya | Banking77 | 0.382 | 27.2% | 0.459 |

Jev は SST-2 と AG News なら 1 割強を人に回すだけで、残りの正解率が 3〜6pt 上がります。Banking77 でも 3 割を回せば、残りは 0.90 近くまで上がります。確率が「間違いやすさ」の手がかりとしてちゃんと機能しているということです。
一方で崩れた Laya の Banking77 は、確率で絞ってもほとんど良くなりません。間違えているのに自信満々（誤答時の確率の中央値 0.97）で、こうなると確率は当てになりません。

ただし Jev の確率も、誤答時の中央値が 0.93〜0.94（AG News）と高めに出ていて、手放しで信じられるほどではありません。閾値はタスクごとに決める必要がありそうです。

### 本題のログ分類

もともとやりたかったのは EC サイトのログを 7 ラベル（payment / auth / performance など）に分けることです。
こちらは 16 件の試し打ちで、Jev 15/16、Laya 14/16、Haiku 16/16、Qwen 15/16 でした。件数が少ないので結論は出せませんが、`INFO auth-svc login success` を Haiku 以外が auth と答えたのは面白い点でした。正解は normal ですが、auth の説明が「Login, session, or token issues」なので、ラベルの定義の方が曖昧だったのかもしれません。

## 昨今の新たなモデル

ベンチマークを回している間にも、新しい判定モデルが次々と出てきました。まだ手元では測れていないので、公表されている情報の範囲でまとめます。

| モデル | 提供元 | 公開日 | 形態 | 入力単価（/1M tokens） |
|---|---|---|---|---|
| d1 | Liquid AI | 9/29 | API。10/7 に d1-3B と d1-omni-600M の重みを公開 | \$0.04 |
| Decisions API（gpt-6-luna） | OpenAI | 9/30 発表、10/6 public beta | API | 非公開（入力のみ課金） |
| Clef / Clef-flash | Cloudflare | 10/1 | Workers AI の API + 重み公開（Apache-2.0） | \$0.24 / \$0.09 |
| pplx-decider | Perplexity | 10/1（v1.1 は 10/6） | API + 重み公開（27B） | \$0.02（v1.1） |

- **d1（Liquid AI）**: API が Jev とまったく同じ形で、URL とモデル名を変えるだけで差し替えられます。後から出た d1-omni-600M は画像や音声も入力でき、端末上での判定を狙っています
- **Decisions API（OpenAI）**: 大手の参入です。考え方は Jev と同じですが、`state` が `input` に、選択肢が配列になるなど、リクエストの形が少し違います。Yes / No の型は `predicate` という名前です
- **Clef（Cloudflare）**: 前述の、LLM を読むだけに使うタイプです。重みは公開されていますが、専用の判定ヘッドが要るので vLLM などではそのまま動きません
- **pplx-decider（Perplexity）**: 27B の重み公開モデルで、v1.1 では入力単価を \$0.02 まで下げました

評価の場も整い始めていて、Hugging Face には判定モデル向けのリーダーボード（Decision Index）ができています。
各社とも「Jev を上回った」と発表していますが、どれも自社計測か、条件の異なるベンチマークでの比較です。この分野はまだ、自分で測らないと分からない段階だと思います。

## 今後の動向の予測

最後に、この 1 か月を見ていて思う、これからの予想を書いておきます。

1. **API の形がそろっていく**  
    d1 と Clef は Jev と同じ形の API を採用していて、OpenAI だけが少し違う形です。チャット API が「OpenAI 互換」に収束したように、判定モデルも `state` + `questions` という形が事実上の標準になっていくと思います。そうなれば、モデルの乗り換えは設定 1 行で済むようになり、価格と精度だけで選ばれる世界になります

2. **単価は 0 に近づき、差がつくのは確率の質になる**  
    1 か月で入力単価は \$0.042 → \$0.02 まで下がりました。出力は最初から無料です。こうなると、正解率に加えて「確率がどれだけ信用できるか（較正）」が勝負どころになるはずです。今回の結果でも、運用で効いてくるのは確率の方でした

3. **LLM と判定モデルの分業が当たり前になる**  
    エージェントが毎ステップ大きな LLM で考えるのではなく、ツールの選択やガードレールのような細かい判断は判定モデルに任せ、自信が無いときだけ LLM や人に回す、という「システム 1 / システム 2」の構成が増えていくと思います

4. **ローカル・端末上への広がり**  
    Laya や d1-omni-600M のように、小さなモデルを手元で動かす流れも続くはずです。ただし今回の Laya の Banking77 のように、小さいモデルには選択肢の数や入力の長さという明確な限界があります。用途に合わせて API と使い分けることになりそうです

一方で、今の判定モデルは英語が中心です。Laya も日本語や文脈に依存する判定は苦手とされていて、日本語の業務データでどこまで使えるかは、これから確かめる価値があると思っています。

自分としては、今回の jevbench の再現で計測の仕組みは確認できたので、次は本題のログ分類のデータを増やして測り直すつもりです。あわせて、d1・Clef・OpenAI の Decisions API も同じ条件で比べてみたいと思います。
